# Два соединения: порядок воспроизведения

Это отдельно подготовленный путеводитель по учебным решениям. Для каждого сценария
нужна новая демобаза из `demo/schema.sql` и `demo/seed.sql`. Откройте два SQL-сеанса A и B
к одной базе, отключите автоматическую фиксацию внутри явных BEGIN и выполняйте шаги
по строкам таблицы. Не запускайте весь файл `src` как один конкурентный сценарий.

Начальный рейтинг заведения `id=1` / `Pizza Hut` равен 4.15.

## Видимость COMMIT — day08_ex00

| Шаг | Сеанс A | Сеанс B | Ожидаемое наблюдение |
|---|---|---|---|
| 1 | `BEGIN; UPDATE pizzeria SET rating=5 WHERE id=1;` | | Транзакция A ещё открыта |
| 2 | `SELECT rating FROM pizzeria WHERE id=1;` | | A видит 5 |
| 3 | | `SELECT rating FROM pizzeria WHERE id=1;` | B видит 4.15 |
| 4 | `COMMIT;` | | Изменение зафиксировано |
| 5 | | `SELECT rating FROM pizzeria WHERE id=1;` | B видит 5 |

## Конкурирующие обновления — day08_ex01 / day08_ex02

1. A: `BEGIN ISOLATION LEVEL READ COMMITTED;` и чтение рейтинга строки `id=1`.
2. B: те же BEGIN и SELECT, до обновления в A.
3. A: `UPDATE pizzeria SET rating=4 WHERE id=1;`, пока без COMMIT.
4. B: `UPDATE pizzeria SET rating=3.6 WHERE id=1;` — команда ждёт блокировку.
5. A: `COMMIT;`. Команда B завершается, затем B выполняет `COMMIT;`.
6. Итог: 3.6. Более позднее присваивание литерала перезаписало значение A.

Повторите на свежей базе с `REPEATABLE READ` в обоих сеансах: после фиксации A
обновление B завершается ошибкой сериализации `40001`. В B нужен `ROLLBACK;`.
Это отличается от арифметического `SET rating=rating+...`: здесь обновляется литерал,
рассчитанный приложением на основе ранее прочитанного состояния.

## Повторное чтение — day08_ex03 / day08_ex04

1. A: BEGIN с выбранным уровнем, затем SELECT рейтинга `id=1`.
2. B: BEGIN, UPDATE этой строки и COMMIT.
3. A: повторный SELECT до собственного COMMIT.

При `READ COMMITTED` второе чтение видит новый рейтинг.
При `SERIALIZABLE` в этом сценарии A продолжает видеть прежний снимок.
Само это наблюдение не доказывает отсутствие всех возможных аномалий сериализации.

## Изменение набора строк — day08_ex05 / day08_ex06

1. A: BEGIN и `SELECT sum(rating) FROM pizzeria;`.
2. B: BEGIN, INSERT новой строки с незанятым ID, COMMIT.
3. A: повторный SELECT суммы до COMMIT.

При `READ COMMITTED` сумма изменится; при `REPEATABLE READ` в PostgreSQL останется прежней.
Для исходных файлов используются ID 10 и 11; при новом запуске они должны быть свободны.

## Взаимная блокировка — day08_ex07

| Шаг | Сеанс A | Сеанс B |
|---|---|---|
| 1 | `BEGIN; UPDATE pizzeria SET rating=5 WHERE id=1;` | |
| 2 | | `BEGIN; UPDATE pizzeria SET rating=4 WHERE id=2;` |
| 3 | `UPDATE pizzeria SET rating=5 WHERE id=2;` — ожидает | |
| 4 | | `UPDATE pizzeria SET rating=4 WHERE id=1;` |

После обнаружения цикла PostgreSQL прерывает одну транзакцию с SQLSTATE `40P01`.
Выбор жертвы не фиксирован. Выполните `ROLLBACK;` в обоих сеансах, чтобы завершить опыт.

## Автоматическая проверка

`python scripts/check.py` сначала проверяет исполнимость восьми исходных файлов
по отдельности на свежих данных. Затем `scripts/isolation_check.py` открывает реальные
соединения и проверяет видимость COMMIT, снимки при трёх уровнях изоляции, новую строку,
ожидание конкурирующего UPDATE, `40001` и `40P01`.
Блокировка синхронизируется через `pg_stat_activity`, а не через фиксированную задержку.
Это дополнительные проверки портфолио, а не исходные школьные тесты.

Основание для ожидаемых эффектов: [PostgreSQL 17 — Transaction Isolation](https://www.postgresql.org/docs/17/transaction-iso.html).
